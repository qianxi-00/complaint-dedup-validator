# 判重算法现状与 LLM 协同优化方案

> 文档性质：只读审计与待审核改造方案。本文不代表已修改、已上线或已验证生产效果。
> 审计日期：2026-09-10。
> 审计范围：`full_corpus.py`、`corpus_parser.py`、`llm_client.py`、`llm_models.py`、`full_corpus_worker.py`、`config.py` 及直接相关测试。未读取 `.env`，未审计真实客户数据。

## 1. 结论摘要

本轮边界：保持现有页面、时间窗口、筛选和两种导出方式不变。用户此前已要求移除“人工禁止共现”功能，因此本文涉及持久化 `cannot_link`、人工复核页面及额外审核流程的内容只属于可选讨论，不纳入首期实施，也不恢复该入口。首期默认对证据不足的候选保留单例，在离线评估报告中复核。

1. **当前线上判重链是纯确定性规则链，不调用 LLM。** Web 创建 comparison 任务后，worker 调用 `FullCorpusService.compare()`；该方法按已存储的 `event_key` 直接分组。`full_corpus.py` 和 `full_corpus_worker.py` 均没有导入或构造 `LlmClient`。
2. **仓库中不存在用于投诉判重的真实业务 LLM 提示词。** 当前仅有两个非业务文本：连接测试提示词“只回复 OK”，以及单元测试传入的占位词“extract”。因此不能把现有判重效果归因于提示词质量。
3. **规则职责集中在字段解析、标准化、问题族识别和事件键生成。** 同键必合并、异键必拆分，中间没有候选相似度、成对证据判断或“不确定”状态。
4. **主要机制风险是离散键的双向放大。** 同一事件只要锚点、类别、街道或机构字符串略有差异就会漏合并；不同事件只要这些字段碰巧相同就会误合并。
5. **建议不是用 LLM 取代规则，而是增加“规则召回候选 + LLM 证据化成对复核 + 保守非传递聚类”。** 硬冲突、精确标识和隐私边界仍由确定性代码控制，LLM 只处理规则无法可靠决定的灰区。

## 4. 真实 LLM 提示词审计

### 4.1 已证实结果

- `src/complaint_dedup/llm_client.py:59-93` 的 `chat_json()` 只接收上游传入的 `messages`，客户端自身不构造业务 system/user prompt。
- `src/complaint_dedup/llm_client.py:129-142` 的连接测试发送“只回复 OK”，用途仅是连通性验证。
- `tests/test_llm_client.py:34-37`、`65`、`91`、`115-118` 使用“extract”作为测试占位消息。
- 仓库当前受审计源码中没有“判断两条投诉是否同一事件”的业务提示词，也没有 prompt 版本号。

**结论：[已证实] 当前投诉判重没有“真实业务 LLM 提示词”；现有判重结果完全由规则和离散事件键产生。**

### 4.2 现有结构若直接接入 LLM 的缺口

`NormalizationDecision` 不能完整表达以下判重必需信息：

- 判定枚举：`same_event`、`different_event`、`uncertain`；
- 支持合并的原文证据与阻止合并的冲突证据；
- 地址、主体、事项、发生对象、订单/平台编号等分维度判断；
- 是否允许自动合并、是否需人工复核；
- prompt/model/rule 版本和可重放输入摘要。

## 5. 当前规则与 LLM 的职责现状

### 5.1 当前规则实际承担的职责

1. **文本清洗与结构提取**：标题清洗、地址优先级、地区/街道、道路门牌、楼栋房间、机构主体、历史工单号、事项片段，见 `corpus_parser.py:180-352`。
2. **类别选择**：优先使用输入类别，再使用四级类别、首个事项片段标签或原始分类字段，见 `full_corpus.py:937-942`。
3. **企业问题族识别**：仅通过三组关键词识别食品安全、欠薪、产品质量，见 `full_corpus.py:33-42`、`1070-1075`。
4. **事件键生成**：
   - 有问题族且有机构：`region + street + organization + family`；
   - 有问题族但无机构：强制单例；
   - 地点未知或类别为空：强制单例；
   - 其他：`region + street + anchor + category`。
   见 `full_corpus.py:1020-1035`。
5. **聚类**：相同 `event_key` 的记录直接进入同组，见 `full_corpus.py:1050-1054`。
6. **人工事后修订**：可重命名事件或把成员移动到新/指定事件，见 `full_corpus.py:710-788`。

### 5.2 当前 LLM 实际承担的职责

**无判重职责。** LLM 客户端和响应模型仅处于可用基础设施/遗留草案状态，worker 没有实例化客户端，也没有在同步或 comparison 中调用模型。

## 6. 漏合并与误合并机制

### 6.1 漏合并机制

| 机制 | 类型 | 说明 |
| --- | --- | --- |
| 离散字符串要求完全一致 | [机制风险] | 普通事件的地区、街道、锚点、类别任一字符串变化都会生成不同键。简称、别名、错别字、语序、门口/附近等表达差异无法被相似匹配补偿。 |
| 解析只保留一个主地址和一个主类别 | [机制风险] | `parse_complaint()` 选择首个地址，类别选择首个可用值；多地址、多事项投诉可能只按第一项建键。测试 `tests/test_corpus_parser.py:192-205` 明确验证只取第一个编号地址。 |
| 问题族无机构时强制单例 | [已证实] | `_event_key()` 对 `family and not org` 返回带 `record_key` 的 singleton；测试 `tests/test_full_corpus_window.py:280-305` 固化了该行为。即使两条投诉有同地点、同事项，也不会合并。 |
| 地点未知或类别缺失时强制单例 | [已证实] | 见 `full_corpus.py:1033-1034`；测试 `tests/test_full_corpus_window.py:339-367` 固化该行为。 |
| 企业跨街道禁止合并 | [已证实] | 企业键包含 street；测试 `tests/test_full_corpus_window.py:309-335` 要求同名企业跨街道保持分离。对跨街道边界、街道解析错误或连锁/大型园区场景，可能形成漏合并，但发生率需标注集验证。 |
| 已提取信息没有进入判重键 | [机制风险] | 道路、门牌、楼栋、单元、房间、商铺号、楼层、历史工单号和事项分段均可被解析，但 `_event_key()` 未直接使用这些结构字段。 |
| 人工拆分不形成后续硬约束 | [机制风险] | comparison 中 `_split_conflicting_groups()` 的 `pairs` 当前固定传空集合；人工移动只修改当前 comparison 快照。后续重跑仍可能按原 `event_key` 再次合并。 |

### 6.2 误合并机制

| 机制 | 类型 | 说明 |
| --- | --- | --- |
| 同键无二次校验 | [已证实] | `event_key` 相同即直接成组，没有成对证据、冲突检查或置信度门槛。 |
| 普通事件键粒度不足 | [机制风险] | 普通键只含 `region + street + anchor + category`。同一小区/企业/路口在不同日期发生的独立事件，只要这些字段相同就会被永久视为同一事件。 |
| 企业问题族过宽 | [机制风险] | 企业键只含主体与三类宽泛问题族。同一企业多次独立欠薪、食品安全或产品质量事件会被合并，未使用发生日期、批次、商品、订单、涉事人员或具体诉求证据。 |
| 关键词子串触发问题族 | [机制风险] | `_issue_family()` 连接标题、类别、诉求后做 `keyword in text`；否定、转述、历史描述或多事项中的关键词也可能触发企业键路径。 |
| 机构抽取采用首个正则命中 | [机制风险] | `extract_organization_subject()` 返回首个符合后缀的候选。投诉同时提及被投诉方、转办单位或其他机构时，主体可能选错；是否在生产数据中频发需抽样确认。 |
| 传递式业务含义被同键桶隐式放大 | [机制风险] | 当前并非显式图聚类，但同一宽键桶内所有成员被无条件视为同一事件，等价于没有成员间冲突检查的全量合并。 |

### 6.3 不应直接宣称的结论

以下均属于 **[待验证假设]**：

- 当前生产环境“漏合并多于误合并”或相反；
- 某个地区、事项类型或企业类投诉是主要错误来源；
- 使用 LLM 后一定能降低总错误率；
- 现有三个企业问题族应扩大、缩小或删除；
- 某个模型、阈值或 token 配置能够满足生产成本和延迟要求。

这些结论必须由标注集、错误切片和影子运行数据支持。

## 7. 推荐目标架构

```text
规则解析与标准化
  -> 高精度硬规则直判（明确同一 / 明确不同）
  -> 多路候选召回（只找可能相同的有限候选）
  -> 规则特征与冲突检查
  -> 模糊候选进入 LLM 成对判定
  -> 程序校验证据与结构化输出
  -> 保守非传递聚类
  -> 自动结果 / 人工复核队列
  -> 保存判定证据、版本与指标
```

职责边界：

- **规则负责**：数据清洗、脱敏、精确标识、候选上限、硬冲突、阈值、证据校验、聚类约束、降级和审计。
- **LLM 负责**：语义别名、叙述差异、多字段综合、是否描述同一具体事件的灰区判断。
- **人工负责**：高风险不确定样本、政策边界样本、冲突样本和新分布样本。
- **LLM 不负责**：直接遍历全库、自由创建聚类、覆盖硬冲突、仅凭置信度自动合并或输出未在输入中出现的证据。

## 8. 分阶段改造方案

### 阶段 0：建立基线，不改变结果

1. 冻结当前规则版本，给 event key 算法增加可追踪版本概念。
2. 从历史人工移动、明显同号/异号样本和分层抽样中建立脱敏标注集。
3. 输出当前规则的 pair、cluster、业务切片指标和典型错误册。
4. 明确“同一事件”的业务定义，尤其是同地点重复发生、同企业多批次问题、多事项投诉和历史工单引用。

验收：任何优化前先能复现当前 comparison 结果，并能解释指标分母、抽样方式和标注一致性。

### 阶段 1：增强规则特征与候选召回，LLM 仅影子运行

1. 保留现有高精度规则结果，新增候选生成，不直接改变事件归属。
2. 对候选执行 LLM 成对判断，记录结果、证据、成本和延迟，但不展示为正式结果。
3. 比较 LLM 与人工标签、当前规则的差异，按错误类型校准 prompt 和门槛。

验收：影子流量不影响现网任务成功率和结果；所有 LLM 决策可追溯、可重放、无明文敏感信息泄漏。

### 阶段 2：只开放“不合并建议”和人工复核

优先让 LLM 识别同键桶内的强冲突，因为拆出疑似误合并比自动扩大合并范围更保守。模型判为 `different_event` 且程序证据校验通过时，只进入人工复核，不自动拆分。

验收：人工复核采纳率、严重误拆率和处理时长达到门槛后再进入下一阶段。

### 阶段 3：开放高置信度自动合并

仅对规则未合并、无硬冲突、证据充分且通过保守聚类约束的候选自动合并。`uncertain`、证据不足或模型失败一律保持规则原结果。

验收：自动合并精确率达到上线门槛，且关键业务切片无明显退化。

### 阶段 4：闭环学习但不在线自训练

将人工复核结果定期进入版本化标注集，用于离线评估、规则表和 prompt 更新。每次变更走固定回归与灰度，不允许模型根据线上反馈自行改变规则。

## 9. 候选召回设计

禁止把全量记录两两发送给 LLM。建议并行使用多路 blocking，取并集后排序、截断：

1. **精确标识召回**：历史工单号、订单号、平台投诉号等一致。精确标识冲突同时作为硬负证据。
2. **地址层级召回**：地区/街道相同，且道路门牌、楼栋房间、商铺号或地点锚点至少一项精确/近似一致。
3. **机构主体召回**：规范机构名、别名表或字符相似度命中，并限制问题族/事项大类。
4. **文本语义召回**：对脱敏后的标题、事项片段、地点摘要生成本地向量，按街道/时间等元数据过滤后取 Top-K。
5. **现有事件邻域召回**：新记录只与候选事件代表记录及少量边界成员比较，不与全库所有成员比较。

建议的硬限制：

- 每条记录候选不超过 20 条，每个召回通道不超过 10 条；
- 默认不跨地区；跨街道仅在精确工单/订单标识或强地址证据存在时进入候选；
- 明确不同的门牌、楼栋、订单号、被投诉主体或事项对象形成 `cannot_link`；
- 候选不足不是错误，保持单例或现有规则结果；
- 候选召回率先用标注集测量，不能只观察最终 LLM 准确率。

## 10. 保守非传递聚类

不得使用“LLM 判 A≈B、B≈C，因此自动推出 A≈C”的普通并查集传递闭包。

建议聚类约束：

1. 每个事件有一个稳定代表记录 `representative`，优先选择证据最完整、标识最多的记录。
2. 新记录加入事件前，必须满足：
   - 与代表记录判为 `same_event`；
   - 与事件内所有硬标识无冲突；
   - 与高风险边界成员不存在 `different_event`；
   - 合并后的事件关键字段仍保持一致或有可解释别名关系。
3. `A-B=same` 和 `B-C=same` 不足以让 C 加入 A 所在事件；至少需要 `A-C=same` 或确定性强证据。
4. 任意 `cannot_link` 优先于 `same_event`，冲突时保持分离并进入人工复核。
5. 对大事件采用“代表 + 最近边界成员 + 冲突字段覆盖”的有限比较，不进行无上限全连接判断。
6. 人工拆分结果应沉淀为跨 comparison 生效的版本化 `cannot_link`，同时允许有审计记录的撤销。

这种方案牺牲部分召回率，换取可控的误合并风险，符合投诉判重中误合并通常更难发现和纠正的保守原则。该优先级仍需业务方确认。

## 11. LLM 成对判重提示词示例

以下是方案示例，不是当前仓库已有提示词：

```text
[System]
你是投诉工单“同一具体事件”复核器。你只能比较输入中的工单 A 和工单 B，
不能创建第三个事件，不能仅因地点或事项大类相同就判为同一事件。

判定标准：
1. same_event：两条工单描述同一时间范围内、同一对象/主体、同一地点、同一具体问题或同一处置链条。
2. different_event：存在明确冲突，或只是同地点/同企业发生的独立问题、不同批次、不同订单、不同对象。
3. uncertain：证据不足、字段冲突无法解释、或需要查看未提供信息。

硬性要求：
- 不得推断输入中不存在的事实。
- evidence_quote 必须逐字来自输入的脱敏文本。
- 如果订单号、平台投诉号、门牌/楼栋/房间、主体或具体事项存在冲突，列入 conflict_evidence。
- 只有 supporting_evidence 足以指向同一具体事件时才能输出 same_event。
- 只输出符合给定 JSON Schema 的 JSON。

[User]
规则特征：
{
  "same_region": true,
  "same_street": true,
  "address_similarity": 0.86,
  "organization_similarity": 1.0,
  "issue_similarity": 0.72,
  "hard_conflicts": []
}

工单 A（已脱敏）：
{
  "record_id": "A",
  "received_date": "2026-09-01",
  "title": "...",
  "address": "...",
  "organization": "...",
  "issue_segments": ["..."],
  "occurrence_ids": ["order:HASH_1"]
}

工单 B（已脱敏）：
{...}

请输出：
{
  "decision": "same_event | different_event | uncertain",
  "confidence": 0.0,
  "supporting_evidence": [
    {"field": "address", "quote_a": "...", "quote_b": "..."}
  ],
  "conflict_evidence": [],
  "reason_code": "EXACT_OCCURRENCE_ID | SAME_SPECIFIC_INCIDENT | FIELD_CONFLICT | SAME_PLACE_DIFFERENT_INCIDENT | INSUFFICIENT_EVIDENCE"
}
```

建议将 prompt、JSON Schema、规则阈值分别版本化；禁止仅修改自然语言提示词而不跑完整标注集回归。

## 12. 证据校验与模型输出防护

LLM 输出通过 Pydantic 结构校验仍不等于业务可信。程序必须追加以下确定性校验：

1. `record_id` 必须严格属于本次候选对，且每对只能有一个最终决策。
2. `decision`、`reason_code` 必须来自枚举，禁止自由文本驱动流程。
3. 所有 `quote_a/quote_b` 必须能在对应脱敏输入中精确定位；找不到即降级为 `uncertain`。
4. 程序重新计算硬冲突；LLM 无权忽略或改写冲突。
5. `same_event` 必须至少有两类独立支持证据，或一个经程序验证的强唯一标识。
6. 仅有“同地区、同街道、同事项大类”不得自动合并。
7. 模型超时、HTTP 错误、JSON 错误、字段缺失、重复决策均保持原规则结果，不允许默认合并。
8. 保存输入摘要哈希、候选特征、模型标识、prompt 版本、响应、校验结果、最终动作和耗时，便于重放审计。

## 13. 成本与延迟控制

1. **两级漏斗**：规则先处理明确同一/明确不同，只把灰区候选发送给 LLM。
2. **事件级复用**：已确认记录先与事件代表比较；相同规范摘要和同版本结果可缓存。
3. **批量但限长**：每次请求包含有限候选对，按估算 token 数切批，不能只按记录数切批。
4. **并发背压**：沿用客户端 semaphore 思路，但将 API/worker 总并发、每任务并发和队列长度分别限制。
5. **预算熔断**：单任务达到候选数、token、费用或时长上限后停止 LLM 扩展，剩余项保持规则结果并标记“未复核”。
6. **超时降级**：模型不可用不能阻塞全量同步；comparison 可按规则结果完成，并单独记录 LLM 覆盖率。
7. **可观测指标**：每千条记录候选数、LLM 调用数、输入/输出 token、缓存命中率、P50/P95/P99 延迟、失败率、降级率。

初始容量建议应通过影子运行确定，不直接沿用 `config.py:43-49` 的通用默认值作为生产判重 SLA。

## 14. 数据脱敏与安全

1. 不向模型发送完整 `raw_json`，只发送判重所需的最小字段。
2. 手机号、身份证、姓名、详细联系方式先替换为稳定占位符；需要判断一致性时发送不可逆 HMAC 指纹或“是否相同”布尔特征。
3. 工单号、订单号和平台投诉号按用途分类：本地精确匹配优先；确需提供模型时使用同批次稳定 token，不发送原值。
4. 地址采用最小必要原则。能用结构化地区、街道、道路、门牌特征完成判断时，不发送完整住址；住宅房间号默认哈希化。
5. 明确模型部署边界、日志保留期和运维访问权限。禁止在应用日志中记录 API key、完整 prompt 或完整模型原始响应。
6. LLM 审计表只保存脱敏输入、摘要哈希和必要证据；原始投诉仍由现有受控数据层管理。
7. 使用固定的脱敏回归测试，验证常见号码、变体格式和多语言字符不会漏脱敏。

## 15. 标注集、评估方法与验收指标

### 15.1 标注集建设

建议至少建立三层数据：

- **随机层**：按月份、地区、街道、事项类别分层抽样，反映总体分布。
- **困难层**：现有同键大桶、近似地址、同企业多事件、多事项、缺失字段、跨街道、人工移动记录。
- **边界层**：业务方明确认为“最容易争议”的同地点重复发生、历史工单引用、转办单位干扰和多订单场景。

每对样本由两名标注员独立判断，分歧交由第三人仲裁；记录 `same/different/uncertain`、理由码和证据。训练调试集、阈值校准集、最终验收集必须隔离，最终验收集在方案冻结前不可用于调 prompt。

### 15.2 必测指标

- 候选召回率：真实同事件 pair 中进入候选集的比例；
- 成对 precision、recall、F1；
- 自动合并 precision 和自动覆盖率；
- B-cubed precision/recall/F1 或同类 cluster 指标；
- 事件纯度、拆分率、误合并事件率；
- 严重误合并数：跨主体、跨明确订单、跨明确地址冲突等；
- 各地区、街道、事项类别、字段缺失程度的切片指标；
- 人工复核率、采纳率、单件耗时；
- 成本、P95/P99 延迟、失败/降级率和可重放率。

### 15.3 建议验收门槛

最终门槛应由业务方在基线测量后确认。建议首轮采用：

1. 高置信度自动合并 pair precision **不低于 99.5%**；
2. 严重误合并在冻结验收集上为 **0**；
3. cluster precision/事件纯度相对现状不下降，且总体漏合并 recall 相对提升 **至少 10%**；
4. 困难层各关键切片 precision 不低于总体值 2 个百分点以上的差距；
5. 候选召回率不低于 **98%**，否则优先改召回而不是改提示词；
6. LLM 结构/证据校验通过率不低于 **99.5%**，失败项全部安全降级；
7. comparison 的 P95 增量延迟、单千条成本和人工复核率达到业务方预先批准的预算；
8. 同一输入、同一规则/prompt/model 版本可重放，最终动作一致率为 **100%**（模型原始措辞可不同）。

## 16. 测试补强建议

当前测试已覆盖解析、确定性企业分组、单例策略、comparison 快照和人工移动，但没有以下业务回归：

1. 同一事件的地点别名、错别字、简称和语序变化；
2. 同一地点/企业在不同日期或批次发生的独立事件；
3. 多地址、多事项分别属于同一或不同事件；
4. 历史工单号、订单号、平台投诉号的一致与冲突；
5. LLM `same/different/uncertain` 的结构、证据和硬冲突覆盖；
6. 非传递三元组：A-B 同、B-C 同、A-C 不同；
7. 模型超时、限流、无效 JSON、重复/缺失 decision 时的安全降级；
8. 脱敏完整性、日志不泄漏和审计重放；
9. 人工 `cannot_link` 在后续 comparison 中持续生效及可撤销；
10. 大桶、候选上限、缓存和预算熔断的容量测试。

## 17. 上线、灰度与回滚

### 17.1 上线策略

1. 所有新逻辑置于明确的算法版本和 feature flag 后，默认继续使用当前规则结果。
2. 先影子运行，再只读展示建议，再开放小比例人工确认，最后才开放高置信度自动动作。
3. 灰度按 comparison 任务或稳定哈希分流，禁止同一任务一半使用旧聚类、一半使用新聚类。
4. comparison 快照保存算法版本、规则版本、prompt 版本和模型标识；旧结果不被后台静默重算。
5. 每次扩量前检查质量、成本、延迟、安全和人工复核五类门槛。

### 17.2 自动停止条件

出现任一情况立即关闭自动动作：严重误合并、precision 低于门槛、模型错误/超时率突增、证据校验失败率超限、成本或 P95 延迟超预算、敏感信息泄漏、结果无法重放。

### 17.3 回滚要求

1. feature flag 一键切回“纯现有规则”模式，LLM 失败不影响同步和 comparison 创建。
2. 新旧结果使用独立 comparison 快照，不原地覆盖旧事件成员。
3. 自动合并/拆分均写不可变审计记录，支持按 comparison 或算法版本重建。
4. 人工确认的 `cannot_link` 与模型建议分开存储；回滚模型版本时不得丢失人工事实。
5. 回滚演练需验证：任务可完成、旧结果可访问、导出一致、无孤立成员、无重复成员、统计可重算。

## 18. 需要业务方审核确认的决策

1. “同一事件”的时间与对象边界，特别是同地点重复发生和同企业多批次问题。
2. 是否正式采用“误合并优先”的保守策略，以及允许牺牲多少 recall。
3. 哪些唯一标识可直接自动合并，哪些冲突必须自动拆分。
4. 住宅详细地址、姓名和各类编号允许进入模型的最小范围及部署边界。
5. 自动合并、人工复核和仅建议三种动作的责任边界。
6. 标注规模、验收门槛、可接受成本和 comparison 延迟预算。

## 19. 建议的审核后实施顺序

在本文通过审核前，不应修改线上算法。审核通过后建议依次实施：

1. 业务定义与标注规范；
2. 基线评估和错误切片；
3. 候选召回与硬冲突规则；
4. 新的成对判重响应模型、提示词和证据校验；
5. 影子运行与离线校准；
6. 保守非传递聚类及持久化人工 `cannot_link`；
7. 小流量灰度、自动停止和回滚演练；
8. 达标后逐步扩大自动覆盖率。

该顺序把“更多使用 LLM”落实为可测、可审计、可降级的协同机制，而不是把现有离散键直接替换为一次不可解释的模型分类。

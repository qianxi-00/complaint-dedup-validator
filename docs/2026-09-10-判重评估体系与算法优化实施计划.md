## 1. 目标与范围

### 1.1 目标

1. 完成当前改造并冻结为**评估基准版本**（唯一 commit + 测试全绿）。
2. 基于本地真实数据建立**可复现评估集**（≥1000 条真实工单，≥400 对标注，真实可溯源）。
3. 建立**评估工具与报告**：一键运行、指标完整、bad case 分类统计、人工可独立阅读。
4. 以评估结果驱动**算法优化迭代**，每次迭代输出优化前后指标对比，且每个 bad case 类别都有回归测试。
5. 建立**回归门禁**：之后任何判重代码修改必须跑评估集回归，防止改坏。

### 1.2 范围外

- 不改页面、时间窗口、导出结构和授权/部署机制。
- 不引入 Milvus/Embedding/Reranker。
- 不在本计划内做本地 vLLM 部署（仅预留配置切换能力）。

## 3. 阶段 B：评估集构建

### B1 数据源与版本绑定

- 数据库：`runtime/local-test-20260910.db`（路径、文件大小、mtime、全文件 SHA-256）。
- 快照：最近一次 completed `sync_runs.id` + 文件哈希；两次 `comparison_runs.id`。
- 构建脚本输出记录上述信息，写入数据集头部 `meta`。

### B2 规模与抽样分层（目标 ≥1200 条真实工单）

| 层 | 抽样规则 | 目标条数 | 用途 |
| --- | --- | --- | --- |
| L1 HBD 同源 | `canonical_work_order_id` 分组含 ≥2 个 HBD 变体 | ≥150 | 强正例 |
| L2 硬合并簇 | 现有 canonical/指纹/订单号硬合并组 | ≥150 | 强正例 |
| L3 规则回退事件 | `rule_fallback` 且事件规模 2-10 | ≥200 | 正/疑似误合 |
| L4 超大事件 | 事件规模 >10（含已知 160/148 条巨类） | ≥150 | 重点负例/争议 |
| L5 漏合并疑点 | 跨事件同标题异分类、同订单号跨事件、同企业跨事件 | ≥200 | 重点正例 |
| L6 未知地点 | `anchor=未知地点` 且文本相似度高 | ≥150 | 困难集 |
| L7 随机层 | 按月份/街道/问题族分层随机 | ≥200 | 总体分布 |

- 去重按 `record_key`；全部编号来自数据库，**禁止编造案例编号**。
- 记录每条样本的来源查询（表名 + 筛选条件），脚本可复跑。

### B3 标注集结构（JSONL）

```jsonc
// records.jsonl
{"record_key":"wo:...","work_order_id":"0826...","hash_id":"a1b2c3",
 "title":"（脱敏）","appeal":"（脱敏）","category":"...","street":"...","anchor":"...",
 "subject":"...","received_at":"...","problem_family":"...","feature_version":"feature-v3",
 "source":{"table":"work_orders","sync_id":"..."}}

// pairs.jsonl
{"pair_id":"P0001","left":"wo:...","right":"wo:...","label":"same|different|uncertain",
 "reason_code":"SAME_INCIDENT|SAME_ENTERPRISE|FOLLOW_UP|SAME_PLACE_DIFFERENT_ISSUE|FIELD_CONFLICT|...",
 "evidence":"...","label_source":"rule_auto|ai_reviewed|business",
 "annotator":"script|AI|人工","notes":"..."}

// clusters.jsonl（事件级）
{"cluster_id":"C0001","member":"[wo:...]","label":"same_event|split","description":"..."}
```

### B4 标注方法与隔离

- 强正例/强负例：由确定性规则自动标注（可验证），并抽样人工复核。
- 困难集：AI 初标 + 人工复核；`uncertain` 单独统计，不计入 P/R 分母。
- 分割：train（40%）/ dev（20%）/ test（40%），test 在优化过程中禁止用于调参。
- 标注一致性：抽查 10% 双人复标，记录分歧率。
- 业务确认：欠薪同企业跨月=同一事件、同地点跨问题族=拆分（已确认），写入 `README-标注规范`。

### B5 脱敏与合规

- 标题/诉求使用现有 `sanitize_for_model`（手机号、身份证、姓名、房间号占位）。
- 提交到 Git 的冻结集：工单号使用固定盐 SHA-256 前 12 位（`hash_id`）；完整映射保留在 `runtime/eval/id_map.json`（不提交）。
- 原始抽样工作稿放 `runtime/eval/`，不入 Git。

### B6 数据一致性校验（防“只看字段存在”）

- 抽样 30 条记录，用脚本对照原始 `半年以来历史表.xlsx`（或最新上传文件）**逐值核对**：工单编号、诉求标题、市民诉求、受理/办结时间；不是只核对列名。
- 核对结果写入评估集 `meta.consistency_check`。

### B7 交付物

`tests/fixtures/dedup_eval/{records,pairs,clusters}.jsonl` + `README.md` + `CHECKSUMS.txt`；`runtime/eval/` 下保留构建脚本输出与 ID 映射。

## 4. 阶段 C：评估工具、指标与报告

### C1 `scripts/build_eval_set.py`

- 入参：`--db`、`--out`、`--seed`、`--target-records`、`--with-consistency-check`。
- 输出：records/pairs/clusters JSONL、`meta.json`（数据源、数量、正负比例、抽样 SQL）、溯源清单。

### C2 `scripts/eval_dedup.py`

- 入参：`--dataset`、`--db`（service 模式）、`--mode engine|service`、`--model`、`--no-llm`、`--concurrency`、`--timeout`、`--seed`、`--limit`、`--compare <baseline.json>`。
- 流程：加载数据集 → 构造记录行 → 调用 `DedupEngine.cluster()`（或 `FullCorpusService.compare()`）→ 与标注对比 → 输出 `runtime/eval/eval_<commit>_<ts>.json` 与报告 Markdown。
- 可重放：记录算法/特征/提示词/模型/配置版本与输入数据集校验和；同一版本结果可复现（模型措辞差异除外）。

### C3 指标（全部写入报告）

- Pair：precision / recall / F1（label=same 为正）、误合并率、漏合并率；
- Cluster：BCubed P/R/F1、事件数、单例率、最大事件规模；
- 严重误合并计数：跨主体、跨明确门牌、跨订单号、跨问题对象；
- LLM：覆盖率、请求数、失败/降级分类、P50/P95 耗时；
- 切片：按问题族、未知地点、HBD、分类、事件规模的指标；
- 前后对比：`--compare` 生成差异表（指标 + bad case 变化）。

### C4 报告模板（独立文件，放 `docs/判重评估报告-YYYYMMDD.md`）

1. 基础信息：评估日期、环境、数据库路径与哈希、数据集版本/条数；
2. 模型信息：服务类型（外部/本地）、实测模型列表、当前模型、不可核验项；
3. 代码版本：分支、commit、tag、工作区是否干净、依赖锁哈希；
4. 评估集来源：抽样分层、正负例比例、标注数量与来源、划分与校验和；
5. 算法说明：五层流程、阈值与版本号、与上一版的差异；
6. 指标结果：总表 + 切片表 + 前后对比；
7. 指标原因分析：每个指标为何高/低（结合决策类型与数据特征）；
8. Bad case 分类统计与明细（每类给出原因、计数、典型案例）；
9. 结论与下轮优化计划。

### C5 版本信息采集（`scripts/eval_versions.py`）

- 代码：`git rev-parse HEAD`、`git tag --points-at`、`git status --porcelain`；
- 模型：`GET /models` 实测 + `LLM_MODEL`；不支持的信息标注“不可核验”；
- 环境：Python 版本、`uv.lock` SHA-256、关键依赖版本（httpx/pydantic/sqlalchemy）；
- 配置：导出非敏感配置键值（排除 `LLM_API_KEY`、`DB_PASSWORD`）。

### C6 测试与门禁

- `tests/test_dedup_eval.py`：加载冻结 mini 集（缺文件则 skip），跑 harness，断言指标不低于冻结门槛；
- Bad case 回归：每个 bad case 类别（见 E1）至少 1 个参数化用例，使用真实脱敏样本构造；
- `AGENTS.md`/`README.md` 增加“修改判重代码必须跑 `scripts/eval_dedup.py`”约定。

## 5. 阶段 D：基线评估与 Bad Case 分析

### D1 运行基线

固定数据集、固定模型（见开放问题 1）、固定参数，运行 engine 模式与 service 模式各一次。

### D2 Bad case 分类体系（报告必须逐类统计）

| 类别 | 子类 | 判定依据 |
| --- | --- | --- |
| 应合未合 | 分类写法差异 / 地点字段差异 / 未知地点 / 跟进单未关联 / 文本低于阈值 / 候选未召回 | 标注 same 但不在同一事件 |
| 不应合已合 | 地点+分类粗键 / 问题族过宽 / 主体抽取错误 / LLM 误判 / 回退无证据 | 标注 different 但在同一事件 |
| 技术性降级 | 模型 429 / 超时 / 无效 JSON / 请求上限 / 解析为空 | 审计 `decision/fallback_reason` |

每个案例包含：真实工单号（或哈希前缀 + 本地映射）、工单标题摘要、事件编号、决策类型、期望/实际、原因码。

### D3 报告 v1

输出 `docs/判重评估报告-<日期>.md`，人工可独立阅读；原始指标 JSON 留在 `runtime/eval/`。

### D4 冻结门槛

以基线指标为下限冻结（如 pair precision 不低于基线、严重误合并不高于基线），写入测试与文档。

## 6. 阶段 E：优化迭代（每次闭环）

每次改动必须：改代码 → 新增/更新单测 → 跑评估集 → 输出前后对比 → 提交。

### E1 已完成/待完成的算法改动（与阶段 A 合并）

- 事件键归一化（分类/问题族）、指纹拆分、历史工单合并、文本重复合并、未知语义修正、主体模糊匹配、时间护栏 shadow。

### E2 评估驱动优化候选（按评估结果取舍）

- 别名表扩充（主体/地址/分类）——由 bad case 高频项驱动；
- 阈值调优（文本相似度、候选分、置信度）——用 dev 集，test 集只做最终验收；
- 批次/并发/超时参数——用评估耗时数据决策；
- LLM 证据字段与提示词迭代（每次提升 prompt 版本并记录）；
- 时间护栏从 shadow 切换为生效（依据 shadow 统计的误拆/误合）。

### E3 Bad case → 测试

每个修复必须附回归用例，命名对应原因码（如 `test_eval_same_case_category_variance`）。

## 8. 验收标准

1. 评估集 ≥1000 条真实记录、≥400 对标注、正负例比例与来源可查、校验和固定。
2. `scripts/eval_dedup.py` 一键复现基线结果；报告内容完整（9 个章节）。

5. 版本信息真实可核验；无法核验项明确标注。

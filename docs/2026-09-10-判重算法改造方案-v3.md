## 三、Phase 1：LLM 链路改造（最高优先级，先拿到稳定能力）

### 3.1 配置变更（按你的要求）

本地 `.env`、`.env.example`、`deploy/env.intranet.example`、内网部署手册同步：

```ini
# 本地模型（OpenAI 兼容）
LLM_BASE_URL=http://<本地模型地址>:8000/v1
LLM_API_KEY=EMPTY
LLM_MODEL=<本地模型名>
LLM_CONCURRENCY=16
LLM_TIMEOUT_SECONDS=200
LLM_MAX_RETRIES=3
LLM_MAX_TOKENS=4096
LLM_ENABLE_THINKING=false
LLM_SEND_ENABLE_THINKING=true        # 按本地服务是否接受该字段调整

# 自动判重
DEDUP_LLM_ENABLED=true
DEDUP_MAX_CONCURRENCY=16             # worker 实际使用该值构建客户端（full_corpus_worker.py:66-70）
DEDUP_MAX_REQUESTS=0                 # 0=不设上限
DEDUP_MAX_SECONDS=0                  # 0=不设上限
DEDUP_CARDS_PER_BATCH=16             # 先 16，评测后可升 24
DEDUP_MIN_CONFIDENCE=0.7

# HTTP 连接池（并发 16 时预留冗余）
HTTP_MAX_CONNECTIONS=32
HTTP_MAX_KEEPALIVE_CONNECTIONS=16
```

关键代码事实：
- `dedup_max_requests=0` / `dedup_max_seconds=0` 已被 `_request_limit_reached`（`dedup_engine.py:568`）和 `_time_limit_reached`（`:574`）识别为不限制。
- worker 构建客户端时传入的是 `settings.dedup_max_concurrency`，`LLM_CONCURRENCY` 只影响直连场景，因此两个都必须设 16。
- `build_llm_client` 会自动放大 httpx 连接池（`llm_client.py:148-176`），但显式设定更清晰。

### 3.2 客户端健壮性（`llm_client.py`）

1. 本地模型响应兼容：
   - `content` 为空时回退取 `message.reasoning_content`；
   - 去掉 ` thinking…<｜end▁of▁thinking｜>` 推理段落后再解析 JSON；
   - 保留并增强 ```json 代码围栏剥离。
2. JSON 修复重试：首次解析/校验失败后，带「上次输出无效 + 校验错误 + 只输出 JSON」的修复提示再试一次，仍失败才抛 `LlmResponseError`。
3. 可选结构化输出：新增 `LLM_JSON_MODE=prompt|json_object|guided_json`（默认 `prompt`）。若本地 vLLM 支持，`json_object`/`guided_json` 可显著降低无效 JSON 率；schema 复用 `EventCardBatchResponse.model_json_schema()`。
4. 退避与限流：429/5xx/超时使用指数退避 + jitter；优先尊重 `Retry-After`（已有基础，补 jitter）。
5. 错误分类统计：连接错误、超时、429、无效 JSON、校验失败分别计数，写入日志与任务结果。

### 3.3 响应模型兼容（`llm_models.py`）

- `null` 字段容忍（本地模型常输出 `"unresolved_card_ids": null`）；
- `decision` 常见变体归一（`merge`/`same` → `same_event`），非法值判为无效组；
- 支持证据字段白名单增加 `location`/`address`（需与地址键相交校验配合，见 Phase 2.5），避免同址同文工单因证据字段不被认可而被拒。

### 3.4 提示词升级 `event-card-v2`

- 明确证据字段枚举与输出 JSON 结构；
- 明确「瞬时事件时间接近是强证据、持续事项可跨月」的判定口径（与 Phase 3 对齐）；
- 无证据输出 `unresolved_card_ids`，禁止编造；
- 禁止输出任何解释性前后缀。

### 3.5 容量与观测

- 容量估算：灰区组件预计 1500~3000 次请求；按 16 并发、单请求 10~30s 估算 20~60 分钟完成任务；实际数据记录后校准 `DEDUP_CARDS_PER_BATCH`。
- 建议新增迁移 `20260910_0005_llm_metrics.py`，在 `comparison_runs` 增加：`llm_requests`、`llm_error_count`、`review_component_count`。同时更新 `tests/test_migrations.py` 的 head 断言。
- 每批审计即时落库，任务失败可定位到具体组件。

### 3.6 验收

- 本地模型连续跑两个窗口：零 429、零容量降级；`llm_coverage ≥95%`；任务正常完成；导出/快照不回归。

## 四、Phase 2：特征与规则归一化（决定“该合能合、不该合不合”）

### 4.1 分类归一（新增 `category_rules.py`）

- 规范规则：
  - 去括号前缀：`（江海）`、`（蓬江）`、`【…】`；
  - 同义映射：`物业费定价过高`/`物业费` → `物业服务纠纷`；`经营噪音`/`生活噪音`/`顾客噪声`/`其他噪声` → `噪声扰民`（保留原始子类展示）；`拖欠、克扣工资`/`其他拖欠克扣工资`/`欠付加班费` → `欠薪`；
  - 组合使用 `category_level_1..4`（当前仅 `category_level_4` 作为兜底，前三级未使用），以稳定层级辅助归一。
- `event_key`/回退键统一使用 `canonical_category`，`category` 原值仅展示与审计。
- 归一粒度（已确认业务口径：同地点 + 同问题族可合，跨族必须拆）：
  - 新增通用 `problem_family` 字段，由 `canonical_category` 映射得到；
  - 草案族表（待业务评审）：`物业与小区管理`、`房屋质量与维修`、`噪声扰民`、`停车与交通`、`市容与流动商贩`、`市政设施`、`消费维权`、`教育培训`、`医疗与医保`、`劳动与社保` 等；
  - 企业问题族（欠薪/食品安全/产品质量）沿用现有 `issue_family`，按「同一企业=同一事件」处理；
  - 硬冲突新增「问题族不一致则拆分」；普通键回退合并升级为「地点 + problem_family」。
- 归一表先以 Python 常量维护（可测试、可评审），后续如需业务维护再加 `runtime/category_aliases.json` 覆盖。

### 4.2 主体归一

- `normalize_organization_name` 增强：去「江门市/江海区」等地区前缀、统一公司后缀；
- 别名词表：`安波福电气系统` = `安波福电器系统`；`西屋厨房家电` = `西屋厨房小家电`；`迪司利光电` 等短名映射到全名；
- 新增 `strong_subjects`（仅保留干净主体：命中企业后缀词典或别名词表、长度合理、不含「市民反映/地址/电话」等噪声）；召回仍可用 `subjects`，但冲突判定与回退键使用 `strong_subjects`；
- `_subjects_match`（`dedup_engine.py:1208`）改为：归一化相等 → 互为子串（较短 ≥4 字）→ 字符 3-gram 相似度 ≥0.8。

### 4.3 地址/锚点归一

- 统一「未知」语义：`未知地点`、`未知街道`、`不详`、`无`、`其他` 在冲突判定中视为空，不再形成假冲突；
- `anchor` 别名词表：`明泰城` = `明泰城小区`；`金瓯路明泰城状元居` 与 `明泰城` 只做候选通道，不直接等价（子小区需保留，避免误合并）；
- 标题二次抽取：当 `anchor` 未知时，用道路+门牌/小区词表从标题再抽取一次锚点候选，写入 `feature_json.anchor_candidates`；
- `location` 写法差异（前缀长短）不得破坏合并：见 4.4。

### 4.4 指纹拆分与跟进单（`dedup_features.py`）

- 拆分字段：
  - `content_fingerprint` = `title + appeal`（**不含 location**），归一化长度 <30 不生成；
  - `location_signature` = `region|street|road|house_no|building`（来自 `explicit_address`）。
- 硬合并链（`_build_event_cards`）调整为：
  1. `canonical_work_order_id` 相同 → 无条件合并（现状保留）；
  2. `previous_work_order_ids` 指向对方 `work_order_id`（跟进单/复查单）→ 合并（**新增**，当前只提取不参与判重）；
  3. `occurrence_ids` 相交 → 无冲突合并（现状保留）；
  4. `content_fingerprint` 相同 + 地址兼容（街道相同或一方缺失，`location_signature` 互为子集或一方为空）→ 合并（**替代原含 location 的指纹**）。
- 新增确定性规则 `text_duplicate`：归一化正文长度 ≥40 且字符 3-gram 相似度 ≥0.90、无硬冲突 → 直接合并。专门用于「未知地点」漏合场景（如中华大道 39 号下水道、麦园云林里违建），不依赖锚点。

### 4.5 硬冲突修正（`_features_conflict`，`dedup_engine.py:994`）

- 只有双方都是**有效**值时才比较（未知/空视为缺失）；
- 街道：双方均已知且不同才冲突（避免「外海街道 vs 未知街道」被误判）；
- 主体：使用 `strong_subjects` + 模糊匹配；
- 地址集合子集规则保留；
- 订单对象冲突保留；
- 「同文本、无有效冲突」的优先级高于字段冲突（内容指纹/文本重复规则先行）。

### 4.6 版本与回填

- `ALGORITHM_VERSION = "event-key-v4"`，`FEATURE_VERSION = "feature-v3"`，`PROMPT_VERSION = "event-card-v2"`；
- 比对时 `_prepare_record`（`dedup_engine.py:582`）已对旧版本自动重算，无需强依赖同步；下次全量同步会重写 `work_orders` 的全部特征列；
- 抽检回填：提供只读对比脚本（新旧 event_key/分组差异报告），确认无损后再上线。

## 五、Phase 3：时间（事件生命周期）的使用方式

> 回应你的顾虑：**时间不做粗筛、不做前置过滤**，只在三个环节以“证据/护栏”方式使用，并可独立关闭。

1. **候选召回与排序（保留现状）**：`_time_bonus`（`dedup_engine.py:1220`）时间接近加分，只影响排序不影响判定。
2. **回退合并护栏（新增）**：`rule_fallback` 合并时，若组内时间跨度 > `DEDUP_FALLBACK_MAX_SPAN_DAYS`（默认 90，0=关闭），则要求该组存在强证据（同一 canonical/occurrence/内容指纹/主体）才允许合并，否则拆分。硬合并与 LLM 判定不受此限制。企业问题族（同一企业=同一事件）不适用护栏，护栏只作用于普通键/问题族合并。
3. **LLM 输入与提示词**：事件卡已含 `time_range`；`event-card-v2` 明确「瞬时事件（噪音/占道/交通/单一故障）时间接近是强证据；持续事项（欠薪/物业/食品/产品质量）可跨月，以主体与问题对象为准」。
4. **可选大桶二次拆分（Phase 1/2 评测后再定）**：仅对「成员 ≥30、时间跨度大、组内平均相似度低」的大事件调用一次 LLM 复核拆分，不参与常规流程。

落地方式：先以 shadow 模式只记录「若启用会拆多少」的统计，确认无误合并/误拆分比例后，再通过配置启用。

## 六、Phase 4：评测集与评测闭环

### 6.1 数据集构建（由我来做）

- 来源：本地全量库 + 两次任务快照 + `comparison_decisions` 审计。
- 分层抽样（第一批 400 对 + 20 个事件级用例）：
  1. 强正例：HBD 组、内容指纹组、同订单号组、跟进单（previous_work_order）、同一企业跨月欠薪组；
  2. 强负例：同街道不同地址、同地点不同问题、同主体不同问题对象、同标题不同对象；
  3. 困难集：未知锚点、多事项、多地址、同地点跨月、同企业多批次、同用户重复投诉。
- 标注规范：沿用 V2 §5 优先级；每条记录 `label`（merge/split/uncertain）+ `reason_code` + 备注。
- 存储（已确认）：
  - `runtime/eval/`：原始抽样与标注工作文件（不入 Git）；
  - `tests/fixtures/dedup_eval/`：脱敏冻结集（`sanitize_for_model` 脱敏 + 工单号哈希）允许提交仓库；`pytest` 在缺少冻结集时跳过而非失败。
- 配套脚本：`scripts/build_eval_set.py`（生成候选对清单 xlsx/jsonl + 标注模板）。

### 6.2 指标与门槛（沿用 V2 §12.2/12.3）

- pairwise precision / recall / F1、BCubed P/R/F1；
- 严重误合并计数（跨主体/门牌/订单/问题对象）；
- 单例率、最大事件规模、跨月合并稳定性；
- LLM 请求数、错误分类、P50/P95 耗时、覆盖率、降级率；
- 门槛：硬合并 precision ≥99.9%；模型合并 precision 目标 ≥99.5%；冻结集严重误合并 0；漏合并比现状下降 ≥20%。

### 6.3 评测执行

- `scripts/eval_dedup.py --dataset <jsonl> --mode baseline|candidate`：离线加载固定工单集 → 调用 `DedupEngine`（不发数据库/页面）→ 与标注比对 → 输出 Markdown/JSON 报告；
- 报告记录 `algorithm_version/feature_version/prompt_version/model_id`，保证可重放；
- pytest 增加 `@pytest.mark.slow` 的小规模评测回归；完整评测手动/发布前执行。

## 八、实施顺序（每阶段可独立回滚）

1. **阶段 1（先做）**：切换本地模型与配置，客户端健壮性，重跑两个窗口 → 拿到覆盖率与耗时基线。
2. **阶段 2**：分类/主体/地址归一 + 指纹拆分 + 冲突修正 + 版本升级 → 用 4.7 案例和现有测试验收。
3. **阶段 3**：时间护栏 shadow 统计 → 按数据决定是否启用。
4. **阶段 4**：评测集标注与 harness（与阶段 1 可并行启动，标注部分需要业务参与）。
5. 全部完成后整库重跑，核对单例率、最大事件规模、导出一致性、审计可追溯。

回滚方式：新规则一律带配置开关（`DEDUP_TEXT_DUPLICATE_ENABLED`、`DEDUP_FALLBACK_MAX_SPAN_DAYS=0` 等），关闭即回到当前行为；算法/特征/提示词版本已持久化，历史任务不受影响。

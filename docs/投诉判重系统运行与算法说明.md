# 投诉判重系统运行与算法说明

## 1. 系统目标

系统维护一份持续更新的全量工单库，并按用户选择的时间窗口执行确定性判重。每次比对结果保存为独立任务快照，历史结果不会被后续同步覆盖。

## 2. 全量同步

- 用户每次上传一份完整 Excel。
- 有工单编号时，以 `work_order_id` 为更新键。
- 无工单编号时，使用标题、诉求正文、地点和受理时间生成复合指纹。
- 同一文件内重复键按最后一行覆盖。
- 新工单插入；已有工单更新结构化字段和原始字段。
- 本次文件缺失的旧工单保留，并标记 `missing_in_latest_upload=true`。
- `sync_runs` 保存同步摘要，`work_order_versions` 保存每次变更前后快照。

## 3. 时间窗口

用户选择 `办结时间` 或 `受理时间`，默认 `办结时间`。

待比对窗口默认取上传文件所选字段的最大自然日。被比对窗口默认取全量库中待比对窗口的补集，两侧无交集、并集覆盖全量库中的有效日期记录。用户也可以手动指定被比对窗口，但必须与待比对窗口不重叠。

所选日期为空的工单进入待比对侧，并单独统计数量。

## 4. 判重规则

普通工单事件键：

```text
地区 + 街道 + 地点 + 事项
```

企业问题族事件键：

```text
地区 + 街道 + 企业/机构主体 + 问题族
```

当前企业问题族只包括：

- 食品安全
- 欠薪
- 产品质量

不同街道不合并，不同问题族不合并。企业主体提取置信度不足时保持单例。系统禁止传递合并，不使用相似度并查集。

## 5. 人工禁止关系

人工保存的 `cannot_links` 关系跨任务长期有效。新建比对任务时，若候选事件中包含禁止共现对，相关记录分别拆为单例。已经生成的历史任务快照不会被自动改写。

## 6. 结果与导出

`comparison_runs` 保存任务参数和统计；`comparison_record_members` 保存任务内工单快照；`comparison_events` 与 `comparison_event_members` 保存任务内事件结果。

导出仍生成“重复项”和“孤立工单”两个工作表，保留冻结首行、自动筛选、事件着色和公式注入防护。

## 7. 部署与授权

生产使用 PostgreSQL 和 Docker Compose，API 对外端口为 `28765`。授权到期日由构建期烧录，上海时区判断；首次启动时间写入 `license_state`，用于检测系统时钟回拨。PyArmor 和外部 OpenAI 兼容模型服务配置保留。

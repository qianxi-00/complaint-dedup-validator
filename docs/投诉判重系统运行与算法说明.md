# 投诉判重系统运行与算法说明

## 1. 系统目标

系统维护一份持续更新的全量工单库，并按用户选择的时间窗口执行自动判重。每次比对结果保存为独立任务快照，历史结果不会被后续同步覆盖。

## 2. 全量同步

- 用户每次上传一份完整 Excel。
- 有工单编号时，以 `work_order_id` 为更新键。
- 无工单编号时，使用标题、诉求正文、地点和受理时间生成复合指纹。
- 同一文件内出现重复工单编号时，不按文件顺序直接覆盖，而是合并非空字段、保留更长文本和更晚时间，并记录全部来源行号。
- 新工单插入；已有工单更新结构化字段和原始字段。
- 本次文件缺失的旧工单保留，并标记 `missing_in_latest_upload=true`。
- `sync_runs` 保存同步摘要，`work_order_versions` 保存每次变更前后快照。

## 3. 时间窗口

用户选择 `受理时间` 或 `办结时间`，默认 `受理时间`。

待比对窗口默认取上传文件所选字段的最大自然日。被比对窗口默认取全量库中待比对窗口的补集，两侧无交集、并集覆盖全量库中的有效日期记录。用户也可以手动指定被比对窗口，但必须与待比对窗口不重叠。

所选日期为空的工单进入待比对侧，并单独统计数量。

## 4. 判重规则

判重分为五层：

1. 同步阶段生成并保存基础工单号、完整内容指纹，以及主体、地址、事项、订单号和文本特征。
2. 对基础工单号相同（含 `HBDn` 转派后缀）、长文本完整重复、发生对象明确相同的记录执行硬合并。
3. 其余记录沿用现行保守规则和主体、地址、事项、订单号、字符 n-gram 候选召回，形成微事件卡。
4. 灰区事件卡按 8-16 张一批交给 OpenAI 兼容模型做互斥分组，程序继续校验硬冲突、置信度、支持证据和输入卡片合法性。
5. 模型不可用、输出非法、达到请求/耗时预算或证据不足时，自动回退到硬匹配和现行保守规则，不阻塞任务。

不同街道、不同问题族不合并。不会仅因相同电话、街道或事项大类合并，不使用无约束相似度传递，也不恢复人工禁止共现功能。

当前企业问题族包括食品安全、欠薪和产品质量。首期不引入 Milvus、Embedding 或 Reranker。

## 6. 结果与导出

`comparison_runs` 保存任务参数、算法/特征/提示词/模型版本和统计；`comparison_record_members` 保存任务内工单快照；`comparison_events` 与 `comparison_event_members` 保存任务内事件结果；`comparison_decisions` 保存自动合并和降级审计。

导出仍生成“重复项”和“孤立工单”两个工作表，保留冻结首行、自动筛选、事件着色和公式注入防护。

## 7. 部署与授权

生产使用 PostgreSQL 和 Docker Compose，API 对外端口为 `28765`。授权到期日由构建期烧录，上海时区判断；首次启动时间写入 `license_state`，用于检测系统时钟回拨。PyArmor 和外部 OpenAI 兼容模型服务配置保留。

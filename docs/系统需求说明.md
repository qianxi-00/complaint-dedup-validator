# 投诉全量工单比对系统需求说明

## 1. 文档目的与系统定位

本文档以当前源码为准，说明系统的业务目标、已实现功能、主要处理流程、数据结构和运行边界，作为后续开发、测试、部署和验收的共同依据。

系统用于维护一份持续更新的全量工单库，并从中选择一个时间窗口作为“待比对”数据，将其与另一时间范围内的工单进行确定性判重，形成可查询、可导出、可审计的比对结果。系统不再区分“历史表”和“每日新增表”两种上传入口；每次同步均上传一份全量 Excel。

## 2. 业务流程

1. 用户上传一份包含全量工单的 Excel、CSV 或兼容格式文件。
2. 系统按工单编号或复合指纹识别稳定工单，新增记录写入全量库，已有记录按最新文件内容更新。
3. 用户选择受理时间或办结时间，并设置待比对起止日期。
4. 被比对时间段可手动指定；不填写时，系统自动取全量有效工单中“不属于待比对窗口”的补集。
5. 后台执行确定性事件分组，保存本次任务的工单和事件快照。
6. 用户在历史比对与事件库中筛选、搜索、查看详情、人工调整展示名称或成员归属，并导出结果。

## 3. 功能需求与现有实现

### 3.1 全量文件同步

- 必填业务字段：工单编号、诉求标题、市民诉求；受理时间、办结时间、事项、地点、处理部门、所属部门等字段按识别结果读取。
- 支持 `.xlsx`、`.xls`、`.csv`；保留原始字段 JSON 和来源行号。
- 有工单编号时使用 `wo:<编号>` 作为稳定键；缺少编号时使用标题、诉求、地点、事项等内容生成复合指纹。
- 同一文件内稳定键重复时以后出现的行覆盖前一行。
- 本次文件缺失的旧工单不会物理删除，而是标记为“未出现在最新上传”；后续比对默认排除这类记录。
- 每次同步记录文件哈希、行数、新增数、更新数、缺失数，并在 `work_order_versions` 保存变更前后快照。

### 3.2 时间窗口比对

- 可选字段：`received_at`（受理时间）或 `completed_at`（办结时间）。当前界面和接口默认使用受理时间。
- 日期按 `Asia/Shanghai` 自然日解释，待比对窗口为闭区间，例如 2026-09-01 至 2026-09-30 包含 9 月 30 日全天。
- 未填写待比对日期时，接口使用全量库该字段的最新本地日期作为单日默认窗口。
- 手动被比对窗口必须同时填写起止日期，且不能与待比对窗口重叠。
- 未填写被比对窗口时，所有不在待比对窗口内的有效工单进入被比对侧，保证两侧互斥并覆盖全量有效工单。
- 比对字段为空的工单当前进入待比对侧，并计入“缺少时间”统计。
- 每次比对都保存独立快照，之后全量库再次同步不会改变旧任务的展示和导出结果。

### 3.3 事件分组与命名

系统采用确定性规则，不依赖 Milvus、Embedding、Reranker 或相似度传递合并。

- 普通工单按“地区 + 街道 + 标准化地点锚点 + 事项”构成事件键。
- 食品安全、欠薪/拖欠工资、产品质量属于企业主体问题族；若能提取高置信企业或机构主体，则按“地区 + 街道 + 标准化主体 + 问题族”分组。
- 不同街道、不同问题族不会合并；提取不到主体、地点未知或事项缺失时采用单例策略。
- 企业或机构名称会进行全半角、空白和后缀规范化。当前合并由规则直接决定，外部大模型配置虽保留，但主流程不调用。
- 事件名称由地区、街道、主体/地点和问题族或事项组合生成，可在详情页人工修改。

### 3.4 任务状态与并发

同步和比对均通过 `processing_jobs` 在后台执行，状态包括“待处理、执行中、已完成、失败”。界面只展示中文状态，不展示进度百分比。

系统采用单任务互斥：当已有同步或比对任务处于待处理或执行中状态时，新的任务直接拒绝并提示已有任务信息，不为用户继续排队。PostgreSQL 部署使用独立 worker；SQLite 开发模式可由 API 启动内嵌 worker。

### 3.5 历史比对与事件库

入口为 `/comparisons`，默认打开最近一次比对任务，历史任务列表和事件列表均分页。

现有事件库支持：地区、街道、处理部门、办结时间范围、仅看无办结时间、仅看含待比对工单、隐藏单例、排序、事件名称/工单/诉求关键字搜索。关键字默认在当前筛选结果内搜索；勾选“全量搜索”后忽略其他筛选条件。事件列表保留“事项”展示列，但不提供事项筛选条件。

事件详情支持分页查看工单，显示受理时间、办结时间、所属部门、处理部门、比对侧、工单编号、诉求标题和市民诉求。市民诉求默认折叠，可逐行展开；用户还可以修改事件名称或将成员移入已有事件/单例事件。

### 3.6 导出

系统保留两种导出：

- 全量导出：导出指定比对任务的全部事件成员。
- 按当前筛选导出：先使用事件库当前筛选条件确定事件集合，再导出这些事件的全部成员，保留完整事件上下文，而不是只导出命中的单条工单。

导出工作簿包含“重复项”和“孤立工单”两个工作表，并保留业务列顺序、事件名称、事件编号、比对侧、事件着色、冻结首行、自动筛选及公式注入防护。

## 4. 数据模型

当前业务数据库由 9 张表组成：`license_state`（授权状态）、`work_orders`（当前全量工单）、`sync_runs`（同步记录）、`processing_jobs`（后台任务）、`work_order_versions`（工单版本审计）、`comparison_runs`（比对任务快照）、`comparison_record_members`（任务工单快照）、`comparison_events`（事件）和 `comparison_event_members`（事件成员）。

`work_orders` 保存最新结构化数据；`comparison_*` 表保存任务级快照，因此历史结果不依赖当前全量库。当前 schema 已为表和字段写入中文数据库注释，时间字段按 UTC 存储、按上海时区解释和展示。

## 5. 接口与页面入口

- `GET /`：工作台、全量上传、创建时间窗口比对、最近任务。
- `POST /sync`：上传全量文件并创建同步任务。
- `POST /comparisons`：创建时间窗口比对任务。
- `GET /comparisons`：历史比对与事件库，支持筛选、搜索、分页和导出入口。
- `GET /events/{event_id}`：事件详情和工单分页。
- `POST /events/{event_id}/name`：保存事件名称。
- `POST /events/{event_id}/members/{record_key}/exclude`：移出事件成员。
- `GET /comparisons/{comparison_id}/export`、`GET /exports/corpus`：全量或筛选导出。
- `GET /jobs/{job_id}`：查询任务状态；`GET /healthz`：健康检查。

## 6. 授权、部署与配置

授权日期通过构建期生成的 `licensing_conf.py` 注入，使用上海时区判断。API 启动、请求中间件和 worker 启动/执行前均检查授权；首次启动时间写入 `license_state`，用于检测系统时间回拨。

生产部署采用 Docker Compose + PostgreSQL，API 容器对外端口为 `28765`、容器端口为 `8765`，worker 负责后台任务。大模型配置保留为内网 OpenAI 兼容服务的扩展配置，但当前确定性比对主流程不调用模型。内网交付时实施人员只需填写模型连接配置；数据库账号、密码、数据库名和内部连接地址由 Compose 管理，API 启动自动创建并校验当前业务表，发现旧表或字段不完整时拒绝启动。授权构建参数、API 密钥和真实数据只允许保存在构建机或服务器运行目录，不得提交到 Git。

## 7. 当前限制与待完善项

1. 当前代码中的任务表仍保留 `progress` 字段，但前端和状态接口不再向用户展示百分比进度。
2. 事件库筛选主要基于任务快照在服务层计算，数据规模扩大后仍需持续评估数据库级筛选和索引优化。
3. 当前详情页成员移出是对单次比对快照的人工调整，不会自动沉淀为下一次比对可复用的“禁止共现”规则；源码中的比对流程也未加载此类关系。
4. 事件名称重构、基于大模型的候选归一化和更复杂的语义判重不属于当前已实现范围。
5. 上传文件缺少工单编号时依赖复合字段生成稳定键；如果这些字段同时发生变化，系统可能将其识别为新工单，需结合业务数据质量持续校验。

## 8. 验收重点

验收应覆盖：全量文件新增/更新/缺失标记、受理/办结时间切换、补集被比对窗口、空时间工单、任务互斥、事件规则边界、筛选与搜索组合、事件详情分页、两种导出结果一致性、历史快照稳定性、授权到期拦截以及 PostgreSQL Docker 部署后的健康检查。

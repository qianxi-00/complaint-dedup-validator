# 判重算法自动化协同优化方案 V2

> 文档性质：已确认实施方案与实现基线。本文覆盖判重算法重构，不改变现有页面、时间窗口和导出业务结构。

## 1. 结论摘要

当前线上判重是纯确定性分组：`FullCorpusService.compare()` 读取全部有效工单，调用 `_normalize_record()` 生成 `event_key`，再将相同 `event_key` 的记录直接作为同一事件。LLM 客户端虽然存在，但 worker、同步和比对流程从未调用它，因此当前没有业务判重提示词参与运行。

现有《判重算法现状与LLM协同优化方案》的判断基本正确，但它仍以“逐对调用模型、人工复核、灰度确认”为主，不适合本项目“每轮全量数据自动完成聚类、尽量不依赖人工”的目标。本方案改为：

1. 先用确定性规则处理明确同一和明确冲突；
2. 将剩余灰区先压缩成“微事件卡”，再批量交给 LLM 做事件卡分组，而不是逐对比较工单；
3. 模型输出只提供候选归并证据，最终由程序执行结构校验、硬冲突校验和保守聚类；
4. 模型超时、限流或输出异常时自动回退到安全规则结果，不阻塞任务；
5. 正常任务不设置人工审批门，人工修订只作为可选事后能力，不作为完成条件。

目标不是让 LLM 替代规则，而是让规则负责高吞吐、确定性和硬边界，让 LLM 只处理规则无法可靠决定的少量语义灰区。

## 2. 真实数据实测

对 `半年以来历史表.xlsx` 的只读分析结果如下：

| 指标 | 结果 | 含义 |
| --- | ---: | --- |
| 数据行数 | 23,478 | 当前全量数据规模 |
| 唯一工单编号 | 23,475 | 有 3 个编号在文件中重复 |
| 受理时间为空 | 0 | 受理时间整体完整 |
| 办结时间为空 | 2,374 | 空办结时间必须作为独立规则场景 |
| 现行事件数 | 19,002 | 相同 `event_key` 直接分组 |
| 现行单例事件 | 16,611 | 单例率约 87.4% |
| 普通键事件 | 18,619 | 现行主体 |
| 强制单例键 | 3,476 | 锚点或企业主体缺失时直接单例 |
| 企业键事件 | 1,383 | 仅覆盖三类企业问题族 |
| 最大事件 | 297 条 | 单键桶过大，不能代表天然同一具体事件 |

字段抽取覆盖也存在明显不足：

- 机构主体为空的记录约 16,716 条，占 71.2%；现行企业合并规则覆盖范围有限。
- 问题族为空的记录约 21,385 条，占 91.1%；食品安全、欠薪、产品质量之外没有通用灰区处理机制。
- 地点锚点为“未知地点”的记录 2,787 条；这些记录即使事项清楚，也会被强制拆成单例。
- 事项分类有 1,235 个不同文本值，同类事项存在括号前缀、四级分类和口径差异，直接字符串相等会制造大量漏合并。

## 3. 最容易被忽略的强信号

### 3.1 `HBD` 派生工单

数据中共有 575 条编号以 `HBD` 结尾的派生工单。去掉末尾 `HBDn` 后，439 个基础编号对应至少两条工单，共 921 条记录。它们通常是同一原始诉求转派给多个处理部门后产生的多行记录。

现行算法已有 392 组能够合并，但仍有 47 组被拆开。典型原因是：

- 基础编号与 `HBD1` 进入不同 `event_key`；
- 不同处理部门或不同分类导致企业键、普通键不同；
- `HBD` 大小写、空白或后缀形式没有统一。

结论：同一“基础工单编号”应作为最高优先级硬合并证据。原始 `work_order_id` 必须保留，另存 `canonical_work_order_id` 仅用于判重。

### 3.2 完全重复的诉求内容

按“标准化标题 + 诉求正文 + 地点 + 受理时间”比较，共有 418 组完全重复内容，涉及 878 条记录。现行算法已有 376 组合并，仍有 42 组漏合并。

结论：长文本完全一致时，可以作为高置信硬合并证据，但必须先做 NFKC、空白、标点、换行和稳定脱敏占位归一化。短标题或短文本不能单独触发硬合并。

### 3.3 普通键既漏合并也误合并

普通键 `地区 + 街道 + 地点锚点 + 事项` 的两个方向都会出错：

- 同一标题、同一地点、同一事项因锚点轻微差异而被拆开；
- 同一小区或路段在不同时间发生的独立问题，因锚点、事项相同被全部合并。

例如现行最大事件包含 297 条工单、44 种不同“标题+诉求”内容，时间跨度超过 50 天。这个桶里可能包含同一物业持续投诉，也可能包含多个独立问题，不能继续用单个离散键直接定稿。

### 3.4 重复工单编号不能最后一行覆盖

文件中存在 3 个重复工单编号。当前同步逻辑在生成 `record_key` 后使用字典去重，同一编号后出现的行会覆盖先出现的行。实测其中一组的两行内容基本一致，但另一组中一行只有处理部门，另一行包含完整诉求正文，按顺序覆盖可能丢失更完整的信息。

V2 要求：

- 完全相同的重复编号行只保留一份逻辑记录；
- 内容不同的同一编号行按字段完整度合并，不能按文件顺序最后覆盖；
- 合并后的来源行号保留在审计字段中，不把同一编号的两行计为两个独立事件。

## 4. 对现有算法方案的复核意见

现有方案保留的主要优点是：强调硬冲突、证据校验、模型失败降级、隐私和非传递聚类。需要调整的地方如下：

| 现有方案 | 本项目问题 | V2 调整 |
| --- | --- | --- |
| LLM 逐对判断 A、B 两条工单 | 23,000 条数据会产生大量调用，速度不可控 | 先形成 8-16 张事件卡，一次请求完成一卡组内的分组 |
| 先人工复核，再小流量灰度 | 与“每轮全量任务自动完成”冲突 | 运行时全自动，离线评测仅用于研发验收 |
| 模型只做候选归一化 | 无法解决跨锚点、跨事项文本的灰区漏合并 | 模型可做批量归并裁决，但不能绕过程序硬约束 |
| 依赖人工 `cannot_link` 长期沉淀 | 与取消人工干预的方向冲突 | 不恢复人工禁止共现，改用硬冲突与自动审计 |
| 没有针对 HBD、重复转派和完整重复文本 | 丢失当前数据中最稳定的判据 | 增加基础工单号、内容指纹、事件卡三层硬匹配 |
| 强调普通相似度召回 | 向量、嵌入和重排会增加部署复杂度 | 首期使用字符 n-gram、结构化字段和现有 LLM，不引入 Milvus |

## 5. 业务判定原则

自动算法必须遵守以下优先级：

1. 同一基础工单编号、同一转派链路：自动合并。
2. 长文本完整重复且没有明确冲突：自动合并。
3. 同一主体、同一具体问题对象、相同地点或同一处置链：允许合并。
4. 仅地区、街道、事项大类相同：禁止自动合并。
5. 不同被投诉主体、不同明确门牌楼栋、不同订单/交易对象、不同具体问题对象：默认拆分。
6. 同一地点重复发生、同一企业多批次问题、同一用户多次投诉但内容和日期不同：进入模型灰区判断，不能仅凭地点或主体合并。
7. 证据不足时保持拆分，但不阻断任务，也不要求人工处理。

时间不是简单硬边界。对于欠薪、物业、食品安全、产品质量等持续性事项，同一对象的问题可能跨月；对于噪音、占道、交通、单一故障等瞬时事项，时间接近度是更强证据。时间字段只参与候选召回和证据评分，不单独决定合并。

## 6. 推荐目标架构

完整流程分为五层：

```text
全量 Excel
  -> 结构化提取与隐私归一化
  -> 硬匹配微聚类
  -> 多路候选召回
  -> 事件卡批量 LLM 裁决
  -> 证据校验、保守聚类、快照持久化
```

### 6.1 结构化提取

在现有 `corpus_parser.py` 基础上，为每条工单生成统一特征对象，而不是只生成一个 `event_key`：

- `canonical_work_order_id`：基础工单编号，去除 `HBDn` 等转派后缀；
- `subject_candidates`：企业、机构、学校、医院、超市、物业、被投诉个人等候选；
- `location_candidates`：地区、街道、道路、门牌、楼栋、单元、房间、商铺和地标；
- `issue_candidates`：按“事项一/事项二/事项三”拆出的多个具体事项；
- `occurrence`：订单号、交易号、平台投诉号、历史工单号、商品、金额、日期线索；
- `time_features`：受理时间和办结时间，保留缺失标记；
- `text_features`：标题、诉求段落的 NFKC 归一化文本和字符 3-gram；
- `privacy_features`：姓名、手机号、身份证号的 HMAC 指纹，不保存模型侧明文。

现有 `extract_previous_work_order_ids()`、`extract_occurrence_identifiers()`、`split_issue_segments()` 已经实现或部分实现，但没有进入当前 `event_key`。V2 必须把它们纳入特征层。

### 6.2 硬匹配微聚类

先处理不依赖模型的确定性边：

1. `canonical_work_order_id` 相同：合并。
2. 完整诉求指纹相同，且归一化正文长度达到阈值：合并。
3. 相同订单号/交易号，且主体和问题对象不冲突：合并。
4. 同一基础编号的不同部门、不同事项文本、不同处理状态：仍合并，但保留部门作为成员属性。

硬冲突优先于硬合并：

- 不同高置信主体且没有别名关系；
- 不同明确门牌、楼栋、房间或订单对象；
- 不同问题对象，例如同一企业下不同的具体产品质量问题；
- 一段文本明确否定了另一段文本的核心主体或事实。

硬匹配后的集合称为“微事件卡”。微事件卡不是最终事件，只表示这些记录在没有模型判断时也足够稳定地属于同一披露链路。

### 6.3 多路候选召回

不要做全量两两比较，也不要只看一个 `event_key`。每条记录或每张微事件卡并行进入以下通道：

1. **编号通道**：基础工单号、订单号、交易号、历史工单号。
2. **主体通道**：规范主体名、主体别名、问题族和街道。
3. **地址通道**：同街道、道路门牌、楼栋单元、商铺、地标。
4. **事项通道**：事项分类树、具体问题短语、标题字符 n-gram。
5. **文本通道**：标题和诉求的字符 3-gram 相似度，不使用外部向量库。
6. **时间通道**：同地址或同主体附近时间窗；时间接近只提升排序，不直接合并。

建议限制：

- 每条记录最多保留 30 个候选，每张事件卡最多保留 12 个代表候选；
- 默认不跨地区；跨街道仅在基础编号、订单号或高置信主体一致时允许；
- 候选集合按“硬证据数、结构化字段匹配数、文本相似度、时间接近度”排序；
- 先召回再截断，不能先按单个 `event_key` 分组后截断。

### 6.4 事件卡

每张事件卡只包含模型判断所需的最小信息：

```json
{
  "card_id": "C001",
  "base_order_token": "H_8F2A",
  "subject": ["万达广场负一楼鹏泰超市"],
  "location": ["江海区外海街道", "万达广场负一楼"],
  "issue": ["食品安全", "商品质量问题"],
  "occurrence": ["订单_H91C", "2026-06-01"],
  "time_range": ["2026-05-13", "2026-07-03"],
  "representative_title": "鹏泰超市消费纠纷",
  "member_count": 5,
  "evidence_snippets": ["同一超市", "购买食品", "要求退款"]
}
```

事件卡禁止包含原始姓名、完整身份证号码、完整手机号和完整住址房间号。模型只判断卡与卡的关系，不接收整库原始 `raw_json`。

## 7. LLM 批量裁决

### 7.1 第一阶段：灰区结构化提取

仅对以下记录调用模型：

- 主体、锚点、订单号或事项抽取失败；
- 一条诉求包含多地址、多主体、多事项；
- 规则候选存在多种解释；
- 文本高度相似但结构化字段冲突。

单批建议 12-20 条短记录，输出结构化 JSON：

```json
{
  "record_id": "R001",
  "subjects": [],
  "addresses": [],
  "issues": [],
  "occurrence_ids": [],
  "hard_conflicts": [],
  "extraction_confidence": 0.0
}
```

抽取结果必须能映射回原文片段；不能定位的证据标记为不确定，不参与硬判断。

### 7.2 第二阶段：事件卡批量分组

一次请求输入一个桶的 8-16 张事件卡，要求模型输出互斥分组：

```json
{
  "groups": [
    {
      "card_ids": ["C001", "C003", "C007"],
      "decision": "same_event",
      "confidence": 0.94,
      "supporting_evidence": [
        {"field": "subject", "cards": ["C001", "C003"], "reason": "同一具体经营主体"}
      ],
      "conflict_evidence": []
    }
  ],
  "unresolved_card_ids": []
}
```

这个设计的关键是：16 张卡一次请求可以隐式完成 120 组卡间比较，模型只需要输出最终分组，不需要逐对返回 A-B、A-C、B-C。它比逐对调用显著节省 token 和网络延迟，也天然避免普通并查集的传递错误。

### 7.3 第三阶段：大桶拆分

当同一宽桶超过 30 张事件卡时：

1. 用“最远优先采样”选 8-16 张差异最大的代表卡；
2. 模型先输出代表卡的互斥分组；
3. 剩余卡先按结构化字段和字符 n-gram 相似度分配到代表组；
4. 只把低置信分配再次送入模型；
5. 任何硬冲突都会取消该卡的自动归并。

这样最大事件从 297 条记录变为多张可控事件卡，不需要把 297 条原文全部放进一个上下文。

## 8. 模型提示词原则

系统提示词应明确以下规则：

1. 只判断输入事件卡是否属于同一具体投诉事件或同一处置链；
2. 不得因为同地区、同街道、同事项大类或相同电话就判为同一事件；
3. 同一主体、同一具体问题对象且无硬冲突时，可以判为同一事件；
4. 明确不同的订单、门牌、商品、对象或事实时，必须拆分；
5. 证据不足时输出 `uncertain`，不得猜测；
6. 只能输出指定 JSON，不得输出解释性前后缀；
7. 不得改写、补全或引入输入中不存在的字段。

提示词、JSON Schema、规则版本和模型版本必须分别持久化。相同输入、相同版本的结果应可重放。

## 9. 自动聚类与安全降级

最终聚类只接受以下动作：

- `hard_merge`：基础编号、完整内容指纹或精确对象标识命中；
- `model_merge`：事件卡模型分组通过结构、证据和硬冲突校验；
- `keep_separate`：模型判为不同、证据不足、发生硬冲突或模型调用失败。

禁止：

- 对模型灰区边直接做无约束传递闭包；
- 将相同电话、相同街道、相同事项大类作为唯一合并依据；
- 模型失败时阻塞整个任务；
- 将模型生成的自由文本直接作为事件键。

最终结果必须满足“一条工单恰好属于一个事件”。多地址、多事项记录可以在每条候选边上使用任一事项扩展召回，但不能因为同一工单包含多个事项而把同一条工单重复放进多个最终事件。

降级顺序为：

```text
事件卡 LLM 自动归并
  -> 硬匹配微事件卡
  -> 现行保守规则
  -> 单条工单事件
```

对模型请求设置任务级候选数、token、调用数和总时长上限。达到上限后，未完成部分自动按安全规则结束，并在任务结果中记录 `llm_coverage` 和 `fallback_count`，不要求人工介入。

## 10. 性能设计

### 10.1 减少重复计算

- 同步时一次性生成并保存结构特征和指纹；
- 比对时只读取需要的字段，不把全部 `raw_json` 发送给模型；
- 使用数据库索引读取候选，不把整库事件在 Python 中反复循环细分；
- 将最终事件和成员一次批量落库，避免逐条 SQL。

### 10.2 LLM 容量预算

建议初始参数：

- 每张事件卡最多 12 个候选；
- 每次请求 8-16 张卡；
- 每个 25,000 条规模任务默认最多 400 次模型请求；
- 并发数 4-8，可按模型服务限流动态下降；
- 相同规则版本、模型版本、事件卡摘要直接命中缓存。

规则阶段应处理绝大多数记录，LLM 只处理灰区。若真实数据中灰区比例过高，应优先增强候选召回与结构化特征，不能单纯提高模型调用量。

## 11. 数据与持久化建议

建议在现有 `work_orders` 增加：

- `canonical_work_order_id`：基础工单编号；
- `complaint_fingerprint`：完整诉求归一化指纹；
- `feature_json`：主体、地址、事项、发生对象和文本特征；
- `feature_version`：特征规则版本；
- `event_key`：保留为兼容字段，但不再作为唯一最终依据。

建议新增比对审计表，记录：

- `comparison_id`、左右事件卡或事件组标识；
- `decision`、`confidence`、`evidence_json`、`conflict_json`；
- `rule_version`、`prompt_version`、`model_id`；
- `fallback_reason`、耗时和 token 使用量。

现有 `comparison_runs`、`comparison_record_members`、`comparison_events` 和 `comparison_event_members` 可以继续保存最终任务快照，但事件键应允许由聚类算法生成，而不是要求所有任务复用同一个离散字符串。

## 12. 评测与验收

### 12.1 评测集

至少建立三类用例：

1. **强正例**：`HBD` 基础编号组、完整文本重复组、明确订单号一致组。
2. **强负例**：同街道不同地址、同地点不同事项、同企业不同问题对象、相同通用标题但地点或对象不同。
3. **困难集**：多事项、多地址、未知锚点、同地点跨月、同企业多批次、同一用户重复投诉。

无标注数据也可以先用于规则覆盖率、候选召回率、事件规模和跨部门合并统计；精确率必须通过人工抽检或业务历史修订记录建立小规模冻结集确认。

### 12.2 必测指标

- 硬合并 pair precision；
- 模型自动合并 pair precision；
- cluster purity、B-cubed precision/recall/F1；
- 严重误合并数：跨主体、跨门牌、跨订单、跨具体问题对象；
- 相对现行算法的漏合并召回提升；
- 单例率、最大事件规模和 1-8 月跨月合并稳定性；
- LLM 请求数、缓存命中率、P50/P95/P99 耗时；
- 模型失败、限流、无效 JSON、证据校验失败后的自动降级率；
- 是否有任何原始 PII 进入模型请求或日志。

### 12.3 建议门槛

- 硬合并 pair precision 不低于 99.9%；
- 模型自动合并 pair precision 目标不低于 99.5%，最终门槛由冻结集确认；
- 严重误合并在冻结集上为 0；
- 相比现行算法，漏合并至少下降 20%，且单例率明显下降；
- LLM 失败不影响任务完成，降级率达到 100%；
- 相同输入和相同版本的任务结果可重放。

## 13. 实施顺序

### 阶段 0：离线特征与基线

实现基础编号归一化、完整文本指纹、主体/地址/事项/发生对象特征，并输出新旧分组对比报告。此阶段不改变线上结果。

验证：HBD 47 个漏分组合并；完整重复文本 42 个漏分组合并；普通键大桶不再直接作为最终事件。

### 阶段 1：规则微聚类与候选召回

增加多路候选召回、硬冲突、字符 n-gram 和时间特征，生成微事件卡。此阶段仍不调用 LLM。

验证：候选召回率和规则 precision 达标，不存在跨地区、跨明确地址和跨订单自动合并。

### 阶段 2：LLM 事件卡批量裁决影子运行

worker 调用模型生成并行建议结果，页面仍展示旧结果。保存模型请求摘要、响应、证据、耗时和降级信息。

验证：与强正例、强负例和困难集比较，确认模型没有把同地点不同问题、同企业不同问题错误合并。

### 阶段 3：切换自动聚类

启用事件卡自动分组，正常任务不设置人工确认门。模型异常时回退到硬微聚类和现行保守规则。

验证：整库重跑无丢失、无重复成员、导出结构不变；任务完成后可使用审计表复现每个合并决定。

### 阶段 4：持续优化

根据离线错误切片调整规则表、候选通道和提示词，不直接在线学习。事件名称的 LLM 优化仍放在最后，避免影响判重主链。

## 14. 单元与回归测试

至少补充以下测试：

1. `HBD1/HBD2/HBD3` 与基础编号合并；
2. 完整重复文本合并，短文本重复不自动合并；
3. 同标题、同地点、同事项在不同具体事件下不误合并；
4. 同主体、同问题族、不同具体对象不误合并；
5. 多地址、多事项记录保留全部候选特征，但一条工单最终只进入一个事件；
6. 未知锚点、未知企业主体不再无条件单例；
7. 相同电话或相同街道不能单独触发合并；
8. 模型输出缺少卡片、重复卡片、非法 decision、证据无法定位时安全降级；
9. 大桶超过 30 张事件卡时分层拆分且结果稳定；
10. 任务失败重试后不产生重复事件成员；
11. 脱敏日志和模型请求中不出现姓名、身份证号、手机号和完整房间号；
12. 现有全量同步、时间窗口、筛选、两种导出和详情页功能不回归。

## 15. 本方案明确不做

- 不引入 Milvus、Embedding 或 Reranker 作为首期依赖；
- 不让 LLM 直接读取整库并决定最终事件；
- 不恢复人工禁止共现功能；
- 不因相同电话、相同街道或相同事项大类自动合并；
- 不用无约束相似度传递和全量并查集把灰区事件连成超大桶；
- 不在本期实现 LLM 自动生成事件名称。

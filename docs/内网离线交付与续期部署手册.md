# 投诉全量工单比对系统内网离线交付与续期部署手册

## 1. 适用范围

本文用于将本项目交付到无外网的 Ubuntu 24.04、x86_64 服务器。应用和 PostgreSQL 均通过 Docker 镜像离线部署，应用容器对外提供 `28765` 端口。当前已在 Ubuntu 22.04.5、`linux/x86_64` 环境验证过构建和运行；目标 Ubuntu 24.04 使用同一 `linux/amd64` 镜像格式，正式交付前仍应按本文完成验收。

本系统每次上传一份全量工单文件，再从全量库中选择待比对时间窗口；未手动指定被比对窗口时，系统使用待比对窗口的补集。当前确定性判重主流程不依赖外部模型，LLM 配置仅为后续扩展保留。

## 2. 交付包内容

构建脚本 `scripts/build_intranet_bundle.sh` 会生成以下文件：

| 文件 | 用途 |
| --- | --- |
| `complaint-dedup-validator-intranet-<日期>.tar.gz` | 已写入授权日期的应用镜像，内含 PyArmor 产物 |
| `postgres-16-alpine.tar.gz` | PostgreSQL 16 Alpine 镜像 |
| `compose.intranet.yaml` | API、worker 和 PostgreSQL 编排，启动时自动初始化表 |
| `env.intranet.example` | 模型连接配置模板，不含数据库配置 |
| `内网离线交付与续期部署手册.md` | 本手册 |
| `SHA256SUMS.txt` | 交付文件校验清单 |

交付包和构建目录不得包含 `.env`、注册码、API Key、客户 Excel、数据库备份或 `runtime` 数据。

## 3. 构建交付包

### 3.1 构建机要求

构建机应为 Linux `x86_64`，安装 Docker、Docker BuildKit、Python 3、`uv`、`sha256sum`，并在首次构建时能够访问 PyPI 和 Docker Hub。构建脚本使用 `--platform linux/amd64`，不要在 ARM 构建机上直接生成交付包。

```bash
cd /path/to/complaint-dedup-validator
chmod +x scripts/build_intranet_bundle.sh
./scripts/build_intranet_bundle.sh --help
```

### 3.2 使用免费版 PyArmor 构建

本项目统一使用 PyArmor 免费版进行混淆，不需要注册码文件，也不要向构建机或交付包加入 `.txt`、`.zip` 注册文件。免费版存在单文件大小限制，超过限制的模块可能保留明文，构建日志会输出 `PLAINTEXT` 警告；交付前必须阅读构建日志并确认实施方接受这一保护边界。

```bash
./scripts/build_intranet_bundle.sh \
  --expire-date 2027-09-01 \
  --image-tag test-2027-09-01
```

脚本会先运行源码测试，再在 Docker builder 中生成 `licensing_conf.py`、执行免费版 PyArmor 混淆，并在 tester 阶段对混淆产物运行测试。出现混淆失败或测试失败时应停止交付，不要用 `--skip-tests` 掩盖问题。

### 3.3 生成校验值

脚本完成后，进入输出目录检查：

```bash
cd build/dist-linux
sha256sum -c SHA256SUMS.txt
tar -tzf complaint-dedup-validator-intranet-bundle-2027-09-01.tar.gz
```

最终交付的是 `*-bundle-<日期>.tar.gz`。授权日期来自构建参数，按上海时区判断，不从客户 `.env` 读取。

## 4. Ubuntu 24.04 离线部署

### 4.1 准备目录和镜像

将完整交付包复制到服务器，例如 `/opt/complaint-dedup-validator`，然后执行：

```bash
sudo mkdir -p /opt/complaint-dedup-validator
cd /opt/complaint-dedup-validator
tar -xzf /path/to/complaint-dedup-validator-intranet-bundle-2027-09-01.tar.gz
docker load -i complaint-dedup-validator-intranet-2027-09-01.tar.gz
docker load -i postgres-16-alpine.tar.gz
docker image inspect complaint-dedup-validator-intranet:latest
docker image inspect postgres:16-alpine
```

应用镜像同时包含日期标签和 `latest` 标签，Compose 默认使用 `latest`。运行数据使用 Docker 命名卷自动持久化，不需要创建宿主机 `runtime` 目录。若使用了手工导出的单标签镜像，先执行：

```bash
docker tag complaint-dedup-validator-intranet:2027-09-01 complaint-dedup-validator-intranet:latest
```

### 4.2 配置和首次初始化

```bash
mkdir -p config
cp env.intranet.example config/.env
vi config/.env
```

环境模板已为每个配置项添加中文注释。模型并发请视本地服务资源修改，
推荐 `8/16`，并将
`DEDUP_MAX_REQUESTS=0`、`DEDUP_MAX_SECONDS=0` 设为不限制请求数和总时长。

只需填写 `LLM_BASE_URL`、`LLM_MODEL` 和对应访问凭据。数据库账号、密码、数据库名、端口和连接地址由 Compose 固定管理，配置文件只保存模型信息，不纳入 Git。

全新数据库初始化：

```bash
docker compose -f compose.intranet.yaml config
docker compose -f compose.intranet.yaml up -d
docker compose -f compose.intranet.yaml ps
curl -fsS http://127.0.0.1:28765/healthz
```

如果启动日志提示发现旧版表或当前表字段缺失，系统会拒绝启动并明确列出问题，应更换为空的 PostgreSQL 数据卷或由项目维护人员处理数据迁移，不要求实施人员手工删除表。

## 5. 授权、续期与回滚

授权模块从构建期生成的 `licensing_conf.py` 读取到期日，使用 `Asia/Shanghai` 当前日期判断。API 启动、HTTP 请求中间件、worker 启动以及领取/执行任务前均会检查授权；首次启动时间写入 PostgreSQL 的 `license_state`，发现系统时间回拨超过 1 天会拒绝服务。

续期不修改客户服务器上的 `.env`。在构建机只需用新日期重新执行免费版 PyArmor 构建，完成校验后交付新镜像：

```bash
./scripts/build_intranet_bundle.sh \
  --expire-date 2028-09-01
```

服务器升级前备份数据库和运行目录；加载新镜像后执行迁移并重启：

```bash
docker compose -f compose.intranet.yaml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > backup-$(date +%F).sql
cp -a runtime "runtime.backup.$(date +%Y%m%d%H%M%S)"
docker load -i complaint-dedup-validator-intranet-2028-09-01.tar.gz
docker compose -f compose.intranet.yaml up -d
```

回滚时停止服务、加载上一个已校验镜像并恢复对应数据库备份；不要只回滚应用镜像而忽略数据库迁移版本。

## 6. 验收和故障排查

```bash
docker compose -f compose.intranet.yaml ps
docker compose -f compose.intranet.yaml logs --tail=100 api
docker compose -f compose.intranet.yaml logs --tail=100 worker
curl -i http://127.0.0.1:28765/
```

验收至少包括：健康检查、上传全量 Excel、插入/更新/缺失标记、受理/办结时间切换、待比对窗口补集、事件详情分页、关键字搜索、筛选导出和全量导出。授权到期或时钟回拨日志出现时，不要修改系统日期或环境变量绕过检查，应重新校准时间或交付新的授权镜像。

常见问题：

| 现象 | 处理 |
| --- | --- |
| `image ... not found` | 确认两个镜像都已 `docker load`，并检查应用是否有 `:latest` 标签 |
| PostgreSQL 不健康 | 检查 `POSTGRES_*` 配置、磁盘空间和 `docker compose logs postgres` |
| 上传/导出权限错误 | 检查 Docker 命名卷状态和 `docker compose logs api` |
| API 反复重启并提示授权到期 | 交付包已过期，重新按新日期构建 |
| 提示疑似时钟回拨 | 校准 Ubuntu 系统时间，确认 NTP 或内网时钟服务正常 |
| 构建输出含 `PLAINTEXT` | 免费版对超限模块的已知限制；核对日志并确认交付保护边界 |
